# 实现清单：cella 图形客户端（Navicat 风格）

> 目标：为 cella 三模块系统补上一个**简约、美观、实用**的图形客户端，
> 让「建表 → 灌数据 → 写查询 → 看结果 → 查诊断」全程脱离命令行。
> 状态：**规划稿，未动工**。按阶段推进，每个阶段独立可构建、可验收、可回退。
>
> **基线版本（2026-09-12 复核）**：编译器 33 用例、存储层 30 用例、整合层 87 用例/765 断言全绿。
> 本轮新增的两个语言级能力 —— **列级 `PRIMARY KEY`** 与 **`rowid` 伪列**（另见
> [`../../cella_db/docs/PLAN_primary_key_rowid.md`](../../cella_db/docs/PLAN_primary_key_rowid.md)）
> 已经落地，本计划原先的最大风险项因此整体降级，见 §6.1。

## 0. 决策速览

| # | 决策点 | 结论 | 理由 |
| --- | --- | --- | --- |
| D1 | 客户端形态 | **内嵌 HTTP 服务 + 浏览器单页应用** | 守住「零第三方依赖」底线；网格/主题/信息密度这类 Navicat 的核心体验，Web 技术栈是成本最低的实现路径 |
| D2 | 代码落点 | **新增顶层模块 `cella_client/`** | 贴合现有「三模块各自独立可构建」结构；`cella_db`/`cella_sql`/`cella_storage` **零改动** |
| D3 | 首版范围 | **核心查询套件** | 覆盖日常 80% 使用场景，是最扎实的第一版；表设计器/导入导出/ER 图留作后续 |
| D4 | 线程模型 | thread-per-connection + `engine_gate_` 全局串行 | `IStorage` 非线程安全，`storage_mutex_` 本来就是串行的；并行只用于静态资源与 JSON 编解码 |
| D5 | 会话模型 | **单会话**：一个服务进程 = 一个连接 = 一个 `Session` | `current_db_` 是引擎级状态，多会话带不来真并发，只会让事务归属变歧义 |
| D6 | 库切换 | v1 单引擎 + `USE` 语义；`EnginePool` 列为 v1.1 可选增强 | 复用现有语义，风险最低；多库真并发在引擎层就要求多实例 |
| D7 | 行编辑定位 | **三级矩阵：主键 → `rowid` → 全列匹配兜底** | 引擎已提供列级主键（唯一 + 非空 + 稳定）与 `rowid` 伪列，见 §6.1 |
| D8 | 总行数 | 懒计数 + 前端缓存，不追求实时精确 | 主键**只做约束、不建索引**，且仍无 COUNT 聚合 → 精确总数必须全表扫，见 §6.2 |
| D9 | 数据浏览默认序 | **有主键 → `ordered <pk> asc`；无主键 → `ordered rowid asc`** | 实测：`UPDATE` 会把该行**物理移到表尾**（§11-3），按 rowid 排序会让刚改的行「跳出当前页」；按主键排序则位置稳定 |
| D10 | 编辑并发 | **乐观校验**：保存时在事务内按定位键重取该行，原值与界面不符则拒绝 | 槽位复用会让陈旧 `rowid` 指向新行；这是兜底手段，见 §6.1 |
| D11 | 前端技术栈 | **原生 ES Module + 自写极简 store，不引入 Vue**；但按「框架无关」结构组织，留好切换门 | 最重的两个组件（虚拟网格、编辑器高亮）本来就得手写 DOM，Vue 帮不上；详见 §5.4.1 |
| D12 | `rowid` 列展示 | **不在网格中显示**，仅内部持有用于行定位 | 对用户是不透明整数，没有阅读价值；保留在列设置里可强制显示（调试用） |

## 1. 目标与非目标

### 想做成的

1. **像 Navicat 那样用**：左边一棵「库 → 表」树，双击表看数据，右键新建查询，写 SQL 按 `Ctrl+Enter` 出表格。
2. **好看**：浅色为默认主题（贴合当前 IDE），紧凑排版、克制的配色、清晰的层次，不花哨。
3. **好用**：结果可排序、可复制、可导出；错误直接指到行列；长查询有加载态；键盘可达。
4. **能看见系统内部**：把 `\stats` / `\locks` / `\waitfor` / `\txn` / `\plan` 这些 CLI 诊断能力图形化 —— 这是 cella 相比通用工具**独有的价值**。

### 明确不做（首版）

- 用户/权限管理（引擎里没有这个概念）
- 备份恢复、定时任务、数据传输向导
- 多连接管理（一个服务进程 = 一个数据目录）
- 跨平台打包分发（先保证 Windows 本机跑通；socket 层预留 POSIX 分支）

## 2. 为什么是「内嵌 HTTP + 浏览器」

三条路都评估过：

| 方案 | 优势 | 否决/采纳理由 |
| --- | --- | --- |
| Win32/Direct2D 自绘 | 真·桌面程序，形态最像 Navicat | 网格控件的虚拟滚动、列宽拖拽、内联编辑、单元格选择区、对话框全要手写，**UI 代码量会远超业务代码**，且纯 Win32 的观感很难做到「美观」 |
| Qt / FLTK / wxWidgets | UI 工作量最小 | 打破「C++17 + 零第三方依赖 + MSVC `/W4 /WX` 单命令构建」的既有约束，构建链和仓库体积明显变重 |
| **内嵌 HTTP + 浏览器** ✅ | 零新依赖，UI 完全自由，迭代最快 | 代价是要新写一个极简 HTTP 服务（Winsock2 约 400 行），以及不自带原生窗口 |

关键判断：**这个项目的技术资产在引擎层，客户端要做的是「把引擎能力暴露好」**。
用 Web 技术栈，能把精力全部投在信息架构、交互细节和视觉打磨上，而不是和 `WM_PAINT` 搏斗。

## 3. 总体架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│  浏览器（纯 HTML/CSS/原生 JS，无构建步骤）                     │
│  左侧树 │ 标签区(查询/数据/结构) │ 结果网格 │ 状态栏            │
└───────────────────────────┬──────────────────────────────────┘
                            │  HTTP/1.1 + JSON  (127.0.0.1:8080)
┌───────────────────────────┴──────────────────────────────────┐
│  cella_client  —— 新增模块                                    │
│                                                              │
│   net/    Socket(Winsock2) │ HttpServer │ Router │ 静态资源    │
│   api/    Json 编解码 │ REST handlers │ SQL 生成器 │ 错误映射   │
│   server/ ApiService（engine_gate_ 串行化）│ 启动参数           │
└───────────────────────────┬──────────────────────────────────┘
                            │  进程内直接调用（不是网络！）
┌───────────────────────────┴──────────────────────────────────┐
│  cella_db_core  （已有，零改动）                              │
│  DbEngine → Session → Executor → IStorage                     │
│           ↑ 复用 CatalogManager 的结构化元数据                 │
└──────────────────────────────────────────────────────────────┘
```

**关键点**：服务端和引擎是**同一个进程**。HTTP 只是「前端与引擎之间的进程内调用」的一层薄壳，
不引入网络传输协议、序列化框架、端口协商这些额外复杂度。

### 3.3 线程与数据流

```
accept 线程 ──每连接 fork 一个 worker──▶  worker 线程
                                            │
              ┌─────────────────────────────┴──────────────────────────┐
              │ 1. 解析 HTTP（无锁，可并行）                            │
              │ 2. 静态资源 → 直接读盘返回（无锁，可并行）               │
              │ 3. /api/* → std::lock_guard<std::mutex> engine_gate_    │
              │              调用 DbEngine / Session（严格串行）        │
              │ 4. JSON 序列化 + 写回 socket（无锁，可并行）             │
              └────────────────────────────────────────────────────────┘
```

- **`engine_gate_` 与 `DbEngine::storage_mutex_` 同构**：既然存储访问本来就串行，
  在 API 层再串行一层不损失任何吞吐，却把「`current_db_` 被并发改写」这类问题的可能性直接归零。
- **锁顺序**：`engine_gate_` → `storage_mutex_`，与既有约定一致，不会引入新的死锁路径。
- 前端单页应用是**串行发请求**的（用户一次只操作一个东西），实际并发度极低。

## 4. 后端设计

### 4.1 极简 HTTP 服务器（零依赖）

只实现 SPA 客户端需要的子集，刻意不做「一个完整 HTTP 框架」：

| 支持 | 内容 |
| --- | --- |
| 方法 | `GET` / `POST`（够用；其余方法返回 405） |
| 版本 | HTTP/1.1，带 `Content-Length`；`Connection: keep-alive` 可选（v1 用 `close`，简单） |
| 请求 | 请求行 + 头部 + 定长正文（`Content-Length`）；**不支持 chunked**（前端不会发） |
| 响应 | 状态行 + `Content-Type` + `Content-Length` + `Cache-Control` |
| 编码 | 全链路 UTF-8；`application/json; charset=utf-8` / `text/html; charset=utf-8` |
| 安全 | 只绑 `127.0.0.1`；静态资源路径规范化后必须在 `web/` 之内（防 `../` 穿越） |
| 限制 | 请求头 ≤ 16 KB、正文 ≤ 8 MB、`recv` 超时 30 s（防挂死连接） |

Windows 细节（会被 `/W4 /WX` 卡住的点）：
`#define WIN32_LEAN_AND_MEAN` + `#define NOMINMAX`、`WSAStartup/WSACleanup` 生命周期、
`ws2_32` 链接（CMake `target_link_libraries(... PRIVATE ws2_32)`）、
`SOCKET` 是 `UINT_PTR` 不能和 `int` 混用（用 `INVALID_SOCKET` 判断）、
`socket` 长度参数用 `int` 不用 `socklen_t`。

### 4.2 JSON 编解码

自己写，约 300 行：

- **编码**：`JsonValue`（null/bool/number/string/array/object）→ 紧凑文本。
  字符串转义覆盖 `"` `\` `\b\f\n\r\t` 与 `< 0x20` 的 `\u00XX`；**中文直接输出 UTF-8 原文**（可读、省字节）。
  数字：整数走 `int64`，浮点用 `%.17g` 再裁剪尾零（保证 double 往返不丢精度）。
- **解码**：只用于请求体（结构固定、简单），支持对象/数组/字符串/数字/bool/null，不追求完备。

> 为什么不用第三方：这是项目红线。而且这里的 JSON 需求确实简单 —— 序列化为主、解析为辅。

### 4.3 REST API 契约

统一响应外形：

```jsonc
// 成功
{ "ok": true, "data": { /* ... */ } }
// 失败（引擎错误、参数错误、内部错误一律走这里）
{ "ok": false, "error": { "code": "DB-502", "message": "表不存在: student",
                          "line": 0, "col": 0, "detail": "【语义错误 SEM-301】..." } }
```

| 方法 | 路径 | 说明 | 落到引擎的什么能力 |
| --- | --- | --- | --- |
| `GET` | `/api/health` | 版本、数据目录、当前库、页大小/缓冲池配置、启动时长 | `EngineConfig` + `current_db()` |
| `GET` | `/api/databases` | 库列表（名称、是否当前库、文件大小） | `ShowDatabases()` + 目录扫描 |
| `POST` | `/api/databases/use` | 切换当前库 `{name}` | `UseDatabase()` |
| `POST` | `/api/databases/create` | 新建库 `{name}` | `CreateDatabase()` |
| `POST` | `/api/databases/drop` | 删库 `{name}`（软删除） | `DropDatabase()` |
| `POST` | `/api/query` | **核心**：执行 SQL `{sql, maxRows}` | `Session::Execute()` → `ScriptReport` |
| `POST` | `/api/plan` | 只编译返回计划 `{sql}` | `Session::CompileOnly()` |
| `GET` | `/api/catalog` | 表清单（表名、表号、列数、建表时间） | `CatalogManager::ListTables()` |
| `GET` | `/api/catalog/{table}` | 列定义（名/类型/长度/NOT NULL/序位/是否主键）+ `primaryKey: {columns: ["id"]}`（**数组，为复合主键预留**） | `FindTable()` → `CatalogTable` + `PrimaryKeyColumnIndex()` |
| `GET` | `/api/tables/{table}/rows` | 取数 `?page&pageSize&sort&order`；**响应固定含 `rowid` 列**；小表一次性全量（§11.7），默认序见 D9（有主键 → 主键升序） | 生成 `get rowid, <全部列> in <表> ordered <默认序> page N, M` |
| `GET` | `/api/tables/{table}/count` | 行数（懒统计，见 §6.2） | 生成 `get <首列> in <表>` 后计数 |
| `POST` | `/api/tables/{table}/rows` | 新增一行 `{values:{列:值}}`（主键冲突 → DB-516） | `INSERT INTO ... VALUES (...)` |
| `PATCH` | `/api/tables/{table}/rows` | 改一行 `{rowid, key:{columns,values}, values}`（`key` 为**元组**，见 §6.1） | 事务内「按定位键重取校验 → `UPDATE ... SET ... limit <定位键>`」 |
| `DELETE` | `/api/tables/{table}/rows` | 删一行 `{rowid, key:{columns,values}}` | 同上，`DELETE in ... limit <定位键>` |
| `POST` | `/api/tables/ddl` | 建表/删表（表设计器用，首版仅 `POST` 原始 DDL） | `Session::Execute()` |
| `POST` | `/api/txn/{begin\|commit\|rollback}` | 事务三件套 | `Session::Begin/Commit/Rollback` |
| `POST` | `/api/checkpoint` | 存盘点 | `DbEngine::Checkpoint()` |
| `GET` | `/api/diagnostics/{stats\|locks\|waitfor\|txn}` | 四项诊断 | `StatsText()` / `LockText()` / `WaitForGraphText()` / `TxnText()` |
| `GET` | `/api/session` | 会话状态（事务号、是否在事务中、已执行语句数） | `Session::StatusLine()` |

**`/api/query` 的响应体**（这是全项目最关键的一个契约）：

```jsonc
{ "ok": true, "data": {
  "session": { "inTxn": false, "txnId": -1 },
  "statements": [{
    "index": 1, "sql": "get rowid, id, name in student", "kind": "GET",
    "line": 1, "col": 1,
    "ok": true, "executed": true, "autoCommitted": false,
    "notice": "",
    "elapsedMs": 0.42, "operatorCalls": 3,
    "affected": 0, "tag": "GET 2",
    "columns": [ { "name": "rowid", "type": "INT64" },
                 { "name": "id",    "type": "INT32" },
                 { "name": "name",  "type": "VARCHAR" } ],
    "rows": [ [393216, 1, "Alice"], [393217, 2, "Bob"] ],
    "truncated": false,
    "error": null,
    "plan": { "before": "...", "after": "..." }
  }]
}}
```

要点：
- **一次请求执行多条语句**，逐条汇报 —— 与 `ScriptReport` 一一对应，编辑器里选中一段也能跑。
- `columns[].type` **引擎没提供**（`ResultColumn` 只有 `name`），因此按「该列首个非 NULL 值的
  `storage::ToString(ValueType)`」推断，全为 NULL 时回退 `"NULL"`。取值范围：
  `NULL / BOOL / INT32 / INT64 / FLOAT / DOUBLE / VARCHAR / CHAR / DATE`。这是必须写进测试的行为。
- **注意两套类型名不要混用**：目录里给的是声明类型（`INT` / `VARCHAR(16)` / `DOUBLE`，来自 `CatalogColumn`），
  值上给的是存储类型（`INT32` / `VARCHAR`）。**表格列头用声明类型**，**对齐与排序判断用值类型**。
- `rows` 里每个值：NULL → JSON `null`；BOOL → `true/false`；数值 → number；字符串 → string。
  **类型保真**，前端不做字符串化，网格按类型右对齐数字。
- `rowid` 是**普通的一列**（`kInt64` 值、列名固定 `rowid`），不特殊对待；但因 `get *` 不会带上它，
  数据浏览接口必须**显式把 `rowid` 写进投影列表**（见 §6.3）。
- `maxRows` 默认 5000，超出置 `truncated: true` 并在状态栏提示「结果已截断」。
- `error` 与 `compileErrors` 合并：编译期诊断取 `cella_errorText()`，执行期取 `DbStatus::ToString()`，
  两者都带 `code` / `message` / `line` / `col`。

### 4.4 单元测试友好性

`ApiService` 设计成**不依赖 socket**：核心方法接收「路由 + JSON」返回「状态码 + JSON」。
HTTP 服务器只是它的驱动。这样绝大多数测试不需要起监听端口。

### 5.4 技术选型

- **无构建步骤**：原生 ES Module（`<script type="module">`），静态服务器直接发 `.js` 即可。
  改完前端刷新浏览器就生效，不引入 npm / bundler / 转译链。
- **无 UI 框架**：自己写 ~30 行的 `h(tag, attrs, children)` 与一个极简的响应式 store（~150 行）。
- **依赖：零**。所有资源本地，不发任何外部请求，离线可用。

#### 5.4.1 为什么不用 Vue（2026-09-12 决策）

不是「Vue 不好」，而是**它恰好帮不上这个界面里最重的两块**：

| 组件 | 谁最重 | Vue 能帮多少 |
| --- | --- | --- |
| 结果网格（虚拟滚动） | 手工 DOM：只渲染视口 ±10 行、复用行节点、列宽拖拽 | **帮不上**。这类组件在 Vue 里反而要 `ref` + `onMounted` + 手动 DOM 去绕过它 |
| 编辑器（高亮叠加层） | 手工 DOM：`<textarea>` 与 `<pre>` 滚动/尺寸同步、单遍扫描上色 | **帮不上**。同上 |
| 树 / 标签 / 面板 / Toast | 条件渲染与列表渲染 | **能帮**，但都是百行级的小组件 |

三条更硬的理由：

1. **约束**：项目红线是零第三方依赖。若真引入，可行路径是 vendored 的
   `vue.esm-browser.prod.js`（约 130 KB）放进 `web/vendor/`，仍能保住「无构建、离线可用」——
   但要往仓库里塞一个体积超过前端自身代码的运行时，性价比不成立。
   而「Vue + Vite + SFC」那条路会直接打破本计划 §5.4 的第一条性质。
2. **规模不到**：一屏最多同时存在 ~50 个网格 DOM 节点 + 几十个树节点，diff 开销没有任何意义。
3. **可读性**：这是个教学项目。前端和 C++ 侧一样应该是「能读懂的资产」。
   150 行 store 的每一行都可追溯，比框架的响应式黑盒更贴项目气质；出问题时调用栈就是自己的代码。

**什么情况下我会改口**：如果后续要持续加**表单密集型**的东西（可视化表设计器、ER 图编辑器、
多语言/主题配置面板），或者前端要交给别人接手 —— 那时框架的边际成本才划算。

**因此留了门（这是重点，比「用不用」更重要）**：

```
web/assets/js/
  store.js     ← 全部状态集中在此，视图层只订阅变化，不反向持有
  api.js       ← 纯 fetch 封装，与框架无关
  *.js 组件     ← 只做「订阅 store → 产出 DOM」，不互相引用
```

约定：**组件之间不互相调用，一律通过 store 交互**。这样将来真要换 Vue，
改的是视图层那几个文件，`store.js` 与 `api.js` **原样复用**。这套结构是框架无关的，
现在不引入框架的成本几乎为零，将来切换的成本也几乎为零。

## 6. 关键约束与风险

### 6.1 🟢 行定位：三级矩阵（2026-09-12 由 🔴 降级）

引擎新提供的两个能力，把这一节从「最高风险」变成了「有明确解法的工程问题」：

| 能力 | 语义 | 客户端价值 |
| --- | --- | --- |
| 列级 `PRIMARY KEY` | 唯一 + 隐含非空；冲突报 `DB-516`；**只做约束、不建索引** | **首选定位键**：稳定、可读、可跨会话复用 |
| `rowid` 伪列 | 物理行标识，值 = `(页号 << 16) \| 槽号`，类型 `INT64`，对用户**不透明** | **次选定位键**：任何表天然都有，不需要建表时做任何事；`limit rowid = X` 走 `GetRecord` **O(1) 直达** |

**定位键选择矩阵**（服务端 `sql_builder` 逐行决定）：

| 表情况 | 生成的定位条件 | 安全性 | 备注 |
| --- | --- | --- | --- |
| 有主键 | `limit <pk列> = <值>` | ✅ 最安全 | 主键值稳定，跨会话、跨请求都能用 |
| 无主键 | `limit rowid = <值>` | ⚠️ 可用 | 需在同一次请求内 fetch → 改；`UPDATE` 后 rowid 会变 |
| 客户端手上没有 `rowid`（例如结果来自手写 SQL、或数据是缓存/导入的） | 全列匹配 `limit c1 = v1 and c2 = v2 …` | ⚠️ 最后手段 | 纯兜底；匹配到 >1 行必须**拒绝修改**并提示改用「打开数据」标签页 |

**把定位键抽象成 `RowKey`（为表级复合主键预留扩展位）**：

引擎当前只支持**列级单列主键**，表级 `PRIMARY KEY (a,b)` 尚未实现
（见 `PLAN_primary_key_rowid.md` §4）。将来一旦支持，定位条件会从「一个列 = 一个值」
变成「一组列 = 一组值」。所以**现在就按元组写，不要按单值写** —— 成本几乎为零，
但省掉将来的返工：

定位键在「前端 → 服务端」之间**以元组形式**传递，由服务端 `api/sql_builder.{h,cpp}` 翻成 `limit` 条件：

```
key = { kind: "primary" | "rowid" | "fullrow", columns: ["id"], values: [7] }

  单列主键  → columns 长度 1
  复合主键  → columns 长度 N          ← 将来引擎支持时，这里零改动
  rowid     → columns = ["rowid"]
  全列匹配  → columns = 该表全部列名

生成规则（NULL 必须走 is null，绝不能生成 `= NULL`）：
  逐列拼 "col = 字面量"，值为 NULL 时改拼 "col is null"，再用 " and " 连接
```

配套的三条约定（都是「不要写死单列」）：

| 位置 | 约定 |
| --- | --- |
| `sql_builder` | 只用 `RowKey` 生成 `limit` 条件，任何地方都不出现「主键就是一个列」的假设 |
| `PATCH` / `DELETE` 请求体 | `keys` 用 `{列名: 值}` 的对象或 `{columns, values}` 元组，**不要**用 `{pk: 值}` |
| `/api/catalog/{table}` | 返回 `primaryKey: { columns: [...] }`（数组），而不是 `primaryKey: "id"`；当前数组长度为 1 |

`rowid` 与全列匹配天然就是元组形式，与复合主键共用同一条代码路径。

`rowid` 有两个语义陷阱，**必须在客户端里兜住** —— 这是本计划剩下唯一需要小心的地方：

1. **`UPDATE` 后 `rowid` 会变**（`UPDATE` = 删旧 + 插新）。
   → 保存成功后**重新取当前页**，绝不能拿旧 `rowid` 接着改同一行。
2. **删除后槽位可能被复用**，陈旧 `rowid` 可能指向另一行。
   → 因此采用**乐观校验**（把「重取 + 比对」和「更新」放进同一个事务）：

```
保存一个单元格（无主键表）：
  BEGIN;
  get <全部列> in <表> limit rowid = <界面上的 rowid>;   ← O(1) 直达
  ├─ 取不到        → ROLLBACK，提示「该行已被删除」，刷新当前页
  ├─ 值与界面不符  → ROLLBACK，提示「该行已被修改」，刷新当前页
  └─ 完全一致      → update <表> set <列> = <新值> limit rowid = <同一个 rowid>;  COMMIT  → 刷新当前页
```

有主键的表可以省掉「重取比对」（主键值稳定），但建议**保留同一条代码路径**，
只在定位条件上分支，以降低测试面。

**NULL 与浮点的处理**：

| 情况 | 处理 |
| --- | --- |
| 列值为 NULL | 条件写 **`col is null`**（`is [not] null` 已支持）；`= NULL` 永远不成立，绝不能生成 |
| 非 NULL 值 | `col = <字面量>`；字符串按单引号转义 |
| 浮点列 | 字面量用 `%.17g` 保证文本可还原；**无主键表一律以 `rowid` 定位，浮点不进条件**，精度风险直接归零 |
| 主键列 | 隐含 NOT NULL，不需要 NULL 分支 |

> **结论：数据编辑面板不但可以做，而且能做得安全。** 原计划排在 P0 的「探针验证 `is null`」一项已关闭；
> 现在 P0 只需要探针确认「`get rowid, <列清单>` + `page` + `ordered rowid` 三者组合」是否如预期工作。

### 6.2 🟡 没有 COUNT 聚合：总行数要全表扫

`grouped` 在本方言里没有聚合函数（`COUNT(*)` 不存在），而**主键是约束、不建索引** —— 两件事都不帮忙。
所以「共 N 行」只能：

1. 服务端 `get <首列> in <表>`（取一列全量）→ 计数 → 缓存（按表名缓存，任何写操作后失效）；
2. 表大时这一步很慢 → 首次访问**异步**做，UI 先显示「≈ 未知」，拿到再补上；
3. 近似计数：用 `among N` 逐级试探上界（可选，不在首版）；
4. 看似可行但其实不行：`get distinct <首列> in <表>` 虽然走了 `grouped` 的去重路径、往返行数更少，
   但它算的是**该列的基数**不是行数（首列重复时结果偏小），**不要用它当计数**。

### 6.3 🟡 `get *` 与 `rowid` 互斥：列清单必须显式展开

`*` 在解析层是**整条语句的独占标志**（`CELLA_Stmt::star`），不能与列清单混写：

```sql
get * in t;                -- ✅ 合法，但结果里**没有** rowid
get rowid, * in t;         -- ❌ 语法错误
get rowid, id, name in t;  -- ✅ 想拿 rowid 只有这一种写法
```

数据浏览接口因此**必须由客户端自己拼出完整列清单**。好在 `/api/catalog/{table}` 已经给了全部列名，
`sql_builder` 拼一行就够：

```
get rowid, id, name, score in student ordered rowid asc page 1, 100;
```

顺带的好处：**列顺序与列别名完全由客户端掌控**，网格列能和目录列严格一一对应。
代价：表结构变化后必须让目录缓存失效，否则列清单会过期 —— 建表 / 删表 / 加列之后统一清缓存。

### 6.4 🟡 服务端串行 → 长查询期间整个客户端「卡住」

`engine_gate_` 串行是必要的，但一次慢查询会阻塞所有请求。
首版策略：前端全局请求串行 + 明显的加载态 + 禁用「执行」按钮 + 超过 5 s 显示「正在执行，请稍候」。
**不做**查询取消（引擎没有中断点，硬取消会留下未定义状态）。诊断面板轮询在请求进行中自动跳过一轮。

### 6.5 🟡 一个数据目录只能有一个服务进程

`IStorage` 直接打开 `.db` 文件，没有文件锁。两个 `cella_web.exe` 指向同一 `--data` 会互相踩。
对策：启动时在 `data_dir` 写一个 `cella-client.lock`（含 pid + 启动时间），已存在则拒绝启动并提示。

### 6.6 🟡 编辑器高亮的正确性

正则做 SQL 高亮对「字符串里的关键字」「注释里的引号」会出错。首版方案：
手写**单遍扫描的高亮器**（状态机：普通 / 字符串 / 注释），而不是正则替换。
约 80 行，正确性足够，且为将来加括号匹配留了钩子。

### 6.7 🟢 其他

| 风险 | 对策 |
| --- | --- |
| 中文（GBK/UTF-8 混用）乱码 | 全链路 UTF-8：HTTP 头显式 `charset=utf-8`、`<meta charset="utf-8">`、CMake `target_compile_options(... /utf-8)`（沿用 cella_db 的做法） |
| MSVC `/W4 /WX` 在 Winsock 上报 warning | 统一 `#define WIN32_LEAN_AND_MEAN` / `NOMINMAX`；`SOCKET` 类型严格区分；不在头文件里 include winsock（只放 `.cpp`） |
| 端口被占用 | 默认 8080，`--port` 可改；占用时给出明确提示并列出可选端口 |
| 浏览器兼容 | 目标 Chrome/Edge 110+（用到较新的 CSS 与 ES Module）；不做降级 |
| `MAX_PATH` | 数据目录与 web 目录用绝对路径 + `\\?\` 前缀兜底（可选） |

## 11. P0 探针实测结果（2026-09-12 已执行）

探针已在本机 Release 构建上跑完。**原计划里「P0 待探针」一项取消，本节即结论**，
下列结论全部有实测输出支撑，不是推断。

### 11.1 ✅ 客户端要生成的查询模式完全可用

```sql
get rowid, id, name, score in s ordered rowid asc page 1, 2;
```

输出列序与投影一致（`rowid` 在最前），页码 1 起，`page 2, 2` 正确取到第 3–4 行。

### 11.2 ✅ `page` 越界 = 空结果，不报错

`page 9, 2`（表里只有 4 行）→ `(0 行)`，无错误。分页控件可以放心把页码翻到任意位置，
但前端要自己判断「空结果 ≠ 出错」。注意区分：`pageNo < 1` 或 `pageSize < 1` 才是 `SEM-311` 错误。

### 11.3 ⚠️ `UPDATE` 会把该行**物理移到表尾**（比原计划写的更严重）

实测（表 `s`，4 行）：

```
初始物理序:  Alice(196608)  Bob(196609)  Carol(196610)  Dave(196611)
update s set score = 99 limit id = 2;
之后物理序:  Alice(196608)  Carol(196610)  Dave(196611)  Bob(196612)   ← Bob 跑到表尾
```

原计划只知道「rowid 会变」，实测是**整行移动到表尾**（删除 + 追加插入）。两个直接后果：

1. 按 `ordered rowid asc` 展示时，用户改完一行**那行会跳到最后一页**，体验上像「数据丢了」。
   → 所以 D9 改为**有主键的表默认按主键排序**，位置才稳定。
2. 「保存成功后重取当前页」是**必须的**，不是可选优化：被改的行很可能已不在当前页。

### 11.4 ✅ 乐观校验的三个分支都能识别，但有一处区分不了

| 场景 | 实测结果 |
| --- | --- |
| `get … limit rowid = <陈旧 rowid>`（该行已被更新过） | **空结果**，不报错 → 判定「已变更」 |
| `get … limit rowid = <当前 rowid>` | 返回该行 → 比对通过 |
| `get … limit rowid = 999999999` | **空结果**，不报错 → 判定「已删除」 |

事务内 `BEGIN → get → update → COMMIT` 全流程正常。

⚠️ **「陈旧 rowid」与「不存在的 rowid」都是空结果，客户端分不清是「被改了」还是「被删了」。**
统一提示为「该行已不存在或已被修改，已刷新当前页」即可，**不要假装能区分**。

### 11.5 ✅ 保留字不能作列名 → `sql_builder` **不需要标识符转义**

方言没有引号/反引号转义机制（词法只接受 `[A-Za-z_][A-Za-z0-9_]*`），但实测：

```
CREATE TABLE t(page INT, …);
→ [语法] SYN-201 @1:16 期望 标识符，实际为 关键字 PAGE
```

即**保留字根本无法被建造成列名/表名**。反过来：**只要表能建出来，它的名字和列名就必然不是保留字**，
客户端把目录里的名字原样拼进 SQL **永远安全**，不存在「列名撞关键字」这种故障。

保留字全表（写 `sql_builder` 与编辑器高亮时直接用这一份，共 51 个）：

```
CREATE TABLE PRIMARY KEY ALTER DROP TRUNCATE RENAME INSERT INTO VALUES UPDATE SET
DELETE FROM WHERE GET IN LIMIT GROUPED HAVING ORDERED AMONG PAGE JOIN ON
LEFT RIGHT MIDDLE UNION DISTINCT AS AND OR NOT NULL TRUE FALSE ASC DESC IS
INT INTEGER FLOAT DOUBLE CHAR VARCHAR TEXT DATE TIME DATETIME
```

### 11.6 ✅ 诊断行列是「语句内坐标」（偏移缺陷已修复，2026-09-12）

`StatementOutcome.line/col`（脚本级）与编译器诊断里的 `line/col`（语句内坐标）**不是同一套基准**。
最初实测发现多语句脚本里诊断行号**恒比语句内行号多 1**（四条语句全部报同一个位置）。

**根因已定位并修复**（见 [`../../cella_db/docs/INTEGRATION.md`](../../cella_db/docs/INTEGRATION.md) §5）：
`SplitSqlStatements()` 原先把语句文本连同**前导换行**一起交给编译器（语句以 `\n` 分隔，累加缓冲时
换行也进了 `st.text`），而 `st.line/col` 却是首个有效字符的绝对位置 —— 两者基准错位一行。
修复：收尾时用 `SkipTrivia` 剥掉前导空白/注释，`st.text[0]` 即 `st.line/col` 指向的字符。

修复后的换算公式（比原来的 `-2` 简单一行）：

```
绝对脚本行 = StatementOutcome.line + (诊断行 - 1)
绝对脚本列 = 诊断列
```

修复后实测（`@L:C` 为语句起点，`@x:y` 为诊断坐标）：

| 语句所在脚本行 | 语句形状 | 诊断坐标 | 按公式换算 | 正确值 |
| --- | --- | --- | --- | --- |
| 3 | 单行 | `1:10` | 3 + (1−1) = **3** | 3 ✅ |
| 4 | 单行 | `1:10` | 4 + (1−1) = **4** | 4 ✅ |
| 5（跨 5–8 行，错误在第 7 行） | 多行 | `3:6` | 5 + (3−1) = **7** | 7 ✅ |

**结论**：客户端「点击错误跳转到编辑器」用 `StatementOutcome.line/col` 定位语句起点，
再用上式换算。写进 `error_map.cpp` 的注释并配单测（上表 3 组即黄金数据）。
另注意：**诊断坐标现在单独可读**（语句内行列），CLI 输出也随之修正。

### 11.7 ⚠️ 分页是「全表物化后切片」→ 小表应改成全量拉取

`Executor::OpPage` 的实现是先跑完子算子（全表 SeqScan，把**所有行读进内存**），再按下标切片：

```cpp
RowSet in;
RunSingleChild(node, ctx, &in);      // ← 全表物化
out->rows.push_back(in.rows[i]);     // ← 然后才切片
```

两个推论：

1. **翻页不随页码变慢**（好），但**每一页都是一次全表扫 + 整表内存物化**（坏）。翻 100 页 = 扫 100 遍全表。
2. 因此 `page 1, M` 取 **M 行**与取 100 行的代价**几乎相同**。

→ **数据浏览改为「一次性全量拉取 + 前端分页」**（阈值建议 2 万行）：

| 表规模 | 策略 |
| --- | --- |
| ≤ 阈值 | 一次 `get <列清单> in <表> ordered <默认序> page 1, <大值>` 全量拉取；**总行数自然已知**，翻页/排序/筛选全在内存里做，交互零延迟 |
| > 阈值 | 服务端分页（`page N, M`）+ 异步懒统计总行数（§6.2） |

好处：**一举解决 §6.2 的总行数难题**（全量拉取时行数就是 `rows.length`），
并把常见规模下的「翻页」从「一次全表扫」降为「零 IO」。这是 P2 的实现依据。

### 11.8 客户端能力边界（实测确认）

| 想做 | 能不能 | 替代方案 |
| --- | --- | --- |
| 删除表 | ✅ `drop table s;` 可用 | — |
| 清空表 | ✅ `delete in s;`（**无条件 DELETE 合法**）可用 | 比 TRUNCATE 慢，语义相同 |
| 给已有表加列 / 改列 / 删列 | ❌ **做不到** | `ALTER`/`RENAME`/`TRUNCATE` 是保留字但**未实现**（`SYN-201 期望 CREATE/INSERT/GET/DELETE/UPDATE/DROP`）。只能 DROP + 重建，且丢数据 |
| 重命名表 | ❌ 做不到 | 同上 |

**这条把「首版不做表设计器」从「范围取舍」变成了「引擎硬限制」**：
表设计器对**新建空表**尚可，对**已有表**完全无解。将来若要做，得先在引擎侧实现 `ALTER TABLE`。

## 附：为什么这一版能真正「实用」

因为它把 cella **独有**的东西做成了界面上的第一等功能，而不是做一个通用的表格工具：

- 执行计划（优化前/后对比）—— 通用工具没有
- 缓冲池命中率、锁表、等待图、事务表 —— 通用工具没有
- 存储层页大小 / 缓冲池帧数 / 替换策略 —— 这是这个项目的教学价值所在
- `cella_catalog` 系统表 —— 天然可作为「系统目录」节点挂进树里，点开就能看到元数据本身
- **`rowid` 伪列**：它把「物理页号 + 槽号」直接暴露成 SQL 可见的值，界面上可以把
  「逻辑行 → 物理位置」的关系画出来 —— 这是把存储层讲清楚的最好教具

客户端不只是「一个更好看的 CLI」，它是这套系统教学演示的入口。

### 本次踩到的坑（记下来省得再踩）

1. `node --check f.js | head && echo ✓` 的 `&&` 绑在 `head` 的退出码上 → 语法错误也显示通过。
   正确写法：`node --input-type=module --check < f.js`（ESM 必须带 `input-type`）。
2. 标签面板从 `display:none` 恢复显示后，浏览器会把 textarea 插入点挪到末尾 → 必须显式还原，
   且要在下一任务再兜一次；`focus()` 应先于还原调用。
3. 测试断言别依赖上一次运行留在 `localStorage` 的状态（诊断子页签、SQL 历史会串场）。

### 布局可拖拽（2026-09-14 追加）

把「该能拖的边」全部做成可拖拽，统一走新模块 `web/assets/js/ui.js`（`makeSplitter` + 偏好读写），
偏好统一存 `localStorage` 的 `cella.ui.*` 前缀，双击手柄复位：

| 拖拽点 | 变量 / 存储 | 范围 |
| --- | --- | --- |
| 侧边栏右边缘（`#sidebarSplit`） | `--sidebar-w` / `cella.ui.sidebarW` | 140–560 |
| 底部面板上边缘（`#panelSplit`，面板隐藏时同步隐藏） | `--panel-h` / `cella.ui.panelH` | 90–640 |
| 编辑器下边缘（`.edresize`，由 `editor.js` 自持） | 元素高度 / `cella.ui.editorH` | 80–900 |
| 表头「#」格下边缘（`.rowresize`） | `--row-h` / `cella.ui.rowH` | 20–64 |
| 表头「#」格右边缘（`.resize[data-ci="-1"]`） | `<colgroup>` / `cella.ui.rownumW` | 34–160 |

行高是**虚拟滚动的关键常量**，改成可变后：`rowH` 参与可视行数（`viewport / rowH`）、滚动行定位
（`scrollTop / rowH`）与上下垫片高度，拖拽时必须 `render()` 重算（不能只改 CSS）；
单元格高度由 `--row-h` 驱动，并配合 `box-sizing: border-box` 让实测行高与 `rowH` 一致。

自测：新增 `web/_selftest/layout.html`（40 项）覆盖夹逼、持久化、双击复位与真实页面拖拽；
`grid.html` 追加垫片随行高重算的断言。前端套件合计 **134 项**。

**⚠️ 拖拽基准的坑（已修，2026-09-14 用户反馈）**：`mousemove` 给的是**相对按下点的累计位移**，
所以基准必须**在按下瞬间取当前实际尺寸**，且移动过程中不能把结果写回基准。
`initSplitters` 最初把启动时读到的 `sw0/ph0` 当基准 → 第二次拖动会**先跳回默认值再跟手**；
`editor.js` 最初写 `height = height + dy` → 一次拖动内**每步累加、跟手速度翻倍**。
现在统一为 `onStart` 里 `getBoundingClientRect()` 取基准 + `base + delta`，
并在 `layout.html` 加了两类回归断言（连续两次拖拽 / 一次拖拽内多步位移）。
